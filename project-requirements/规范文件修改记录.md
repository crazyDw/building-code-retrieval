# 规范文件修改记录

## 1. 目的与适用范围

本文档记录规范 Markdown 语料的**规范化修改方式与过程**，供后续新语料入库时照此执行，也可用于追溯已发生的改动。

适用范围：`数据库上传资料/` 目录下的规范 Markdown 文件。本文档只涉及**标题标记的规范化**，不涉及正文、条款内容、表格与公式。

## 2. 语料源约定

| 位置 | 角色 | 说明 |
|---|---|---|
| `数据库上传资料/` | **语料源（唯一）** | 位于工作区内，5 个 `.md` 平铺。后续所有读写只针对此处。（2026-10-04 由 `规范文档/` 改名） |
| `建筑规范/markdown/` | **只读备份** | 位于工作区外，按 `名称/名称.md` 分目录。**不再作为语料源，也不随语料源更新而同步。** |

两处经实测为**独立副本**（`st_ino` 各不相同），修改一处不会影响另一处。备份保留了**未规范化的原始形态**，可作为解析器的回归测试夹具。

## 3. 为什么需要规范化

PDF → Markdown 的转换由外部工具完成，其输出在标题标记上**不一致**。首批 5 份文件实测存在三种形态，并伴随两类结构错误：

| 文件 | 规范化前的章节标记状态 |
|---|---|
| 民用建筑通用规范 | 章 `#`、节 `##`（已是目标形态） |
| 住宅项目规范 | 章 `#`、节 `##`（已是目标形态） |
| 钢结构通用规范 | 章全部用 `##`；**目次条目 `8 维护与拆除…… 19` 带 `##`** |
| 混凝土结构通用规范 | 5 个章 `##` + 1 个章 `#`；**10 条正文条款被标为 `##`** |
| 砌体结构通用规范 | 5 个章 `##` + 1 个章 `#` |

两类错误的实际后果：

- **目次条目带标记**：会被误判为章。钢结构通用规范的章数会从 8 多算成 9；若用"第一个章标题"界定正文起点，起点会被误定在目次内部。
- **条文被标为标题**：这 10 条会从条款列表中消失。混凝土结构通用规范的条数会从 99 少算成 89。

## 4. 目标形态

1. **章**用 `#`
2. **节**用 `##`
3. **前言、目次**用 `#`（与章平级的前置条目）
4. **目次条目不带标题标记**（它是列表内容，不是标题）
5. **条文不带标题标记**（`X.Y.Z` 开头的行是正文）

## 5. 修改方式

采用「**按行号定位 + 内容断言**」的脚本方式，而非按内容全局替换。原因：条文的标题行很长（含中文标点与条号），按内容匹配容易因空格或标点差异而失配，或误伤正文中同形的句子。

执行约束：

- **先断言、后写入**。逐行核对目标行的现有内容是否符合预期（必须为 `## ` 开头且不是 `### `）；任一行不符即**整体跳过该文件**，不部分写入。
- **只改行首标记**，行内其余字符原样保留，包括行尾空格。
- **保持原文件属性**：编码 UTF-8（无 BOM），行尾分隔符沿用原文件的 `\n`。
- **改前先试运行**，打印逐行前后对照，确认无误后再落盘。

## 6. 修改过程

1. **普查**：扫描全部语料的标题结构，统计章、节、条、款、项的数量与标记形态，识别异常。
2. **试运行**：按行号读取待改行，断言内容符合预期，打印「原行 → 新行」对照，不写文件。
3. **落盘**：断言全部通过后写入，逐文件报告改动行数。
4. **回读验证**：
   - 标题异常数应为 0（即不存在"章非 `#`、节非 `##`、前置非 `#`"的情况）
   - 条款数与预期一致
   - 条款编号零缺口

## 9. 未处理项

**标题内的版式残留空格保留在源文件中**，不做清理。实测共 12 处 / 6 种：`总 则`×5、`设 计`×2、`目 次`×2、`场 地`、`声 环 境`、`燃 气`（2026-10-04 逐行复核修正，原记「5 处」）。

保留原因：这是 PDF 匀字排版的痕迹，属转换工具产物；解析器会在**内存中归一化**（`总 则` → `总则`）后再用于章节路径与界面展示，因此不影响功能。若后续决定清理源文件，按本文第 5 节的方式执行即可。

## 10. 后续新文件的操作流程

1. 将新规范的 `.md` 放入 `数据库上传资料/`。
2. 跑结构普查，输出章、节、条、款、项的数量与标记形态。
3. 若有异常（章非 `#`、节非 `##`、目次条目带标记、条文被标为标题），按第 5 节方式试运行后落盘。
4. 回读验证：标题异常数 0、条款数与预期一致、编号零缺口。
5. 记录本次改动（文件、行数、行号清单）到本文第 7 节。

## 11. 附：解析器仍需容错的原因

规范化是**便利**而非**前提**。解析器按行首文本的**编号形态**判断层级（带小数点的段数区分章/节/条/款/项），不依赖 `#` 标记数量：

| 行首形态 | 判定 |
|---|---|
| 带标记 + `X.Y.Z` | 条（被误标的，还原为条文） |
| 带标记 + `X.Y` | 节 |
| 带标记 + `X` | 章 |
| 无标记 + `X.Y.Z` | 条 |
| 无标记 + `X` | 款 |
| 无标记 + `X）` | 项 |

这样即使新文件仍带转换工具的原始缺陷，也能正确入库，不必每次先人工收拾。本文记录的修改只是让源文件更易阅读与校对。
