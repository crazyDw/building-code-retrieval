## 二、v1 范围与完成定义

### 2.1 端到端最小闭环

```
Markdown 语料 → 解析/切块 → SQLite（真相源）→ Milvus（派生）
→ 查询理解 → 双路召回 → RRF → 重排 → 按条聚合 → 上下文组装
→ DeepSeek 生成（默认/深度）→ SSE → Web 界面
```

### 2.2 v1 必须满足

- 分层答案：`<!--推导-->` 在前、`<!--原文-->` 在后，视觉严格区分；条号引用可点击。
- 只依据检索条文作答，每条结论挂 `clause_id`；未命中明说并给最接近条款；禁止引入规范外知识。
- 允许条件性推导（写明输入值），禁止合规结论。
- 全文强制性规范标注；命中被替代老标准时给出适用性提示（v1 只做标准级）。
- 数值校验分层：原文层逐字核对，推导层只要求写明输入值。
- 降级语义如实暴露：API 失败退纯检索、GPU 不可用跳过重排、超限整条丢弃。
- 条款号直查短路；引用侧栏显示完整章节路径；表格命中展示整表并高亮行；节内条数提示。
- 项目条件条可抽取、可手改、手改后锁定。
- 深度分析按钮：走 `deepseek-flash` + thinking，推理过程放折叠面板。
- 开发模式 `DEV_MODE=true` 不依赖 GPU 可跑通界面与接口（检索用 SQLite 简单关键词模拟，见 D8）。
- 会话上下文：只带本轮召回条款 + 被显式引用过的历史条款（用户在消息里写了条号，或点击过引用链接），不累积；协议见 D11。
- 宽泛问题给 8–10 条起步条文并明示「这不是完整清单」；多子问题先反问澄清先回答哪一个。
- 项目条件由服务端抽取、前端可手改；用户锁定的条目在后续轮次优先，模型不得覆盖。
- `DEV_MODE` 在界面、日志与 `/api/health` 显式标注，其结果不得作为检索质量依据。

### 2.3 v1 不做

按《项目概况》第八节执行，关键项：PDF→Markdown 转换本身、按专业拆章、跨规范对比、条文级失效映射、地方标准与图集、节级检索块、会话历史持久化、用户反馈闭环、微调、账号权限、Milvus GPU 索引、本地大模型生成、CI。

## 三、v1 技术决策（M0 写入 docs/architecture）

| 编号 | 决策 | 理由 | 回退 |
|---|---|---|---|
| D1 | 包划分按本文件第四节执行：`config/logging/errors/tokenizer` + `corpus/store/retrieval/generation/api` 六块 | 与《项目概况》数据流的分层一一对应，依赖单向 | 实现中发现职责重叠时先改文档再动代码 |
| D2 | 依赖策略：`project/pyproject.toml` 用 setuptools + src 布局（`package-dir = {"" = "src"}`），声明除 torch 外的运行依赖；torch 按 README 固定命令手动安装，不写进 `dependencies` | 避免任何路径把 cu126 版覆盖成 CPU 版；setuptools 不引入新的离线依赖 | 若 FlagEmbedding 触发了 torch 重装，改用 `requirements-torch.txt`（带 `--index-url`）单独先行安装 |
| D3 | 进程模型：单个 uvicorn 进程（**强制 `workers=1`**）内加载 bge-m3 与重排模型，lifespan 里预热完成后才置就绪；模型推理用单把互斥锁串行化（线程池 + CUDA 并发会放大显存峰值）；`DEV_MODE=true` 跳过；模型进程禁用调试器 | 单机单用户，延迟最优、部署最简；多 worker 会让显存与实际模型数翻倍 | 显存冲突时拆成模型服务（v1 不做，只记录） |
| D4 | 前后端同源：Vite build 产物由 FastAPI 静态挂载 `/`；开发期 Vite proxy 到 8000 | SSE 同源、无 CORS、少一个常驻进程 | 部署问题出现时再拆端口 |
| D5 | 存储实现：stdlib `sqlite3` + 手写 DDL（`PRAGMA user_version` 管版本），不引 ORM/Alembic；pymilvus 同步客户端；Milvus 重建 = drop + create + 从 SQLite 全量重嵌入 | 规模只有 554 条条文，简单可靠优先 | 结构变更频繁时再引迁移工具 |
| D6 | 检索链路同步实现；SSE 用 `StreamingResponse`，阻塞调用放线程池；生成侧用 `langchain-deepseek` | 与《关键决策记录》一致：LangChain 只管生成 | 流式问题无法解决时改用官方 HTTP SDK |
| D7 | 配置用 `python-dotenv` 读 `.env`；相对路径一律相对仓库根解析（从 `config.py` 的位置推），不依赖 cwd | 从任何目录启动行为一致 | 无 |
| D8 | `DEV_MODE=true`：SQLite 文件与 Milvus collection 名加 `_dev` 后缀（不建向量、不写正式库），仅入库《民用建筑通用规范》，跳过模型加载与预热；检索退化为 SQLite 关键词（LIKE）模拟 | 界面与接口开发不占 GPU，也不污染正式数据 | 无；其结果不得作为检索质量依据 |
| D9 | 标准号映射表直接解析 `数据库上传资料/规范标准号映射表.md`（唯一来源，不派生 CSV）；同步更新 `.env` / `.env.example` 的 `STANDARD_MAP_PATH` | 避免两份数据不同步 | 无 |
| D10 | 降级与就绪行为：CUDA 可用 + `RERANK_ENABLED=true` 为完整路径；开关为 false 属主动配置，只置 `rerank_used=false`、不置 degraded；CUDA 不可用时 embedder 回退 CPU 加载并置 degraded（原因码 `gpu_unavailable`）、重排跳过（不回退 CPU 重排）；embedder 也加载失败则启动失败并明确报错（不提供半可用检索）；Milvus 启动时不可达则 fail fast，运行中断开则 chat 返回错误事件、health 置不健康 | 与铁律 16 和需求一致，避免含糊的「半可用」状态 | 无 |
| D11 | 会话上下文：服务端不持久化会话；`/api/chat` 请求带 `referenced_clause_ids[]`，由前端在用户消息出现条号或点击引用链接时收集；服务端只组装「本轮召回 + 这些历史条款」 | 满足「不累积」的上下文要求，又不引入会话存储（v1 明确不做） | 若后续要历史，改为服务端会话表 |
| D12 | Milvus 度量：dense 用 FLAT + COSINE；sparse 用 SPARSE_INVERTED_INDEX + IP（Milvus 稀疏向量不支持 COSINE）。与《项目概况》「FLAT + COSINE」的字面差异记入 `docs/architecture/` | 按库的实际能力落地，避免 M3 卡在不可行的索引定义上 | 无 |

### 并行开发说明

**主线与副线**：主链（M1 解析 → M2 切块入库 → M3 向量/Milvus → M4 检索 → M5 生成 → M6 chat 集成）必须串行；可并行的三条副线是：

1. 前端线（M7）：`docs/api/` 契约与 SSE 事件定稿后，即可用 mock 数据开发，最后接真实后端联调；
2. 语料派生批处理线（M2 之后）：题库/对抗集、词表候选、50 条核对清单的生成与人工审核，不碰检索代码；
3. 生成侧与运维准备线：M0 的 API 冒烟完成后即可开发 `client.py` 与 prompt 草案（用固定条文夹具），runbook、备份/降级脚本、README 随时可起草。

**硬约束**

- 语料真相链 parser → chunker → ingest → embedding → Milvus 是硬串行，上游没产出时下游只能对假数据开发。
- GPU 独占：模型加载、重排基准、阈值标定、延迟实测不能同时跑（8 GB 显存互相挤占）。
- Milvus 启停期间不做集成测试与索引重建；常驻时占用 1.5–2 GB 内存。
- API 批处理（题库/词表）不与延迟测试并发，避免额度消耗与耗时数据互相干扰。
- 共享文件单写者：`models.py`、`config.py`、`pyproject.toml`、`docs/api/`、`conftest.py`、`ingest.py` 同一时间只由一条线修改。

**并行上限与启动点**：本机建议同时跑 2–3 条开发线 + 1 条验证线（子代理上限 4 条，不含主线程，再多会被 GPU/内存/额度抵消）。M0 本身很小，拆并行收益有限；第一个真正的并行窗口是 M1 的 `models.py` 冻结之后，收益最大的提前启动点是 M7 前端、M4 题库/词表批处理、M5 生成侧 client/prompt。
