# 关键决策记录

本文件记录本项目需求阶段确定的全部关键决策及其理由。决策以对语料的实测为依据——实测数据见《项目概况.md》，语料规范化的过程见《规范文件修改记录.md》。

| 决策 | 理由 |
|---|---|
| 语料整部收录，不按专业拆章 | 人为取舍会造成引用缺块——"建筑设备"章里也有与建筑做法直接相关的要求。代价是提示词与术语表要覆盖机电。 |
| 层级判定以编号形态为主、`#` 标记为辅 | 实测 5 份文件出现三种标记形态（章全 `##`、章标记混用、已规范化），且同一文件内也可能不一致。按 `#` 数量判层级必然出错。 |
| 解析器完全容错，不依赖源文件书写形式 | 转换工具的缺陷形态多样且不可控。把容错放在解析器里，新文件无论规范与否都能入库，不必每次先人工收拾。 |
| 源文件仍做规范化（49 行） | 便于人工阅读、校对与 diff；与解析器解耦后，规范化是便利而非前提。 |
| 款项打包成块，超限时在项边界切分 | 项与款共享前置条件（如「严禁用于下列混凝土结构：」），劈开会让每一片都失去适用前提。实测本批语料中唯一超过 256 token 的款单元——《混凝土结构通用规范》`4.4.9` 款2（含 3 个项、225 字 ≈ 270 token）——恰好含项，说明"项不拆"与"块 ≤ 256 token"会真实冲突。解法是切分位置取项边界：款连同其项打包，超限时在项边界切成多块，共享 clause_id 与款号；仅当单个项自身超限时才在其内部按句切。项不脱离的是款的标识，不是款的物理块。 |
| 按款切分时，条的引导句单独成块 | 引导句不属于任何款，若不单列，"按款切"这条规则就有例外分支。它本身几乎不会被召回，且命中后组装时仍还原为整条，所以独立成块不影响答案完整性。整条未超限、不触发切分时，引导句仍留在整条块内。 |
| 长款按句切分时以项为最小边界 | 项与款共享前置条件，把项切成两半会让每一片都失去适用前提。本批语料的项都落在短款里，这条约束是为后续规范预留的。 |
| 目次区间按「目次」标题界定，跳过带页码的行 | 目次条目本身可能带 `##` 标记，若用"第一个章标题"界定正文起点，会被误定在目次内部。 |
| 长条文按款切分并共享 clause_id | 按条文正文计量（不含表格），住宅项目规范有 3 条正文超 256 字，最长 `4.2.2` 达 329 字。这已不是边缘保护而是必须实现的功能；款级切块保证重排能看到完整块，同时入上下文时仍还原整条。 |
| 维持「超 256 token 才按款切」，不改为总是按款切 | 实测总是切款会把块数从 698 增到 992（+42%），而款块中位仅 32 字、47% 在 30 字以内。更要紧的是同一条的多个款块前缀相同、正文只有十几字，向量高度雷同，会一起挤占候选名额却只对应同一条，压缩其他条款的覆盖；且 5 份语料中含款的条 100% 是「一个引导句 + 同质清单项」结构，款间无主题差异，切款带不来区分度。规则简化也不成立——长度检测与按句切分仍然要做，只是判断从条下移到款。 |
| 合并单元格按 colspan/rowspan 展开填充 | 混凝土结构通用规范出现合并单元格，不展开会导致行块的条件列错位，用户会把数值套到错误的条件上。 |
| LaTeX 符号还原为可读文本，并写入查询扩展表 | 28 处 LaTeX 实为符号与单位而非公式。用户不会输入 `E_h,av`，只会问"水平照度平均值"，原文若只有符号则向量与关键词都匹配不上。 |
| 引用图以「条→表」为主、「条→条」为辅 | 实测住宅项目规范 10 处表引用、0 处条引用，与另一份比例完全相反。原设计中条引用优先的假设不成立。 |
| 返回条数从 6 提到 10，重排候选从 15 提到 25 | 实测条文中位 47–54 字，原参数按"条文较长"估。10 条仍远低于上下文上限，覆盖更全而成本几乎不变。 |
| 表格命中时展示整表并高亮行 | 表格各行是互斥对比关系（不同楼梯类别对应不同数值），只给一行会让用户看不到对比。 |
| 命中表格行时送入整条条文，不单列"送整张表" | 与条文块统一为一条规则，避免两条规则在同一场景下冲突。同时引用多张表的条文（如 `3.1.1`）会把两张表一并送入——选哪张表的判据写在条文正文里，一并送入让模型据此判断；代价是多带一张可能无关的表，在千 token 量级可接受。 |
| 嵌入前缀加入章节路径 | 最短条文仅 11 字，向量高度泛化。带上主题词可显著提升区分度，成本仅为拼接时多带一个字段。 |
| 表题与「注：」并入表格行块前缀 | 「注：」是表格的适用范围限定。若不可检索，用户问"托儿所的楼梯踏步"会命中表行却漏掉限定。 |
| 条号存数值分量 | 字符串排序会把 `5.3.10` 排在 `5.3.9` 前面，章节树、条文列表、引用排序全都会错。 |
| 检索结果标注节内条数并提供展开入口，而非新增节级检索块 | 用户问"某一节有什么要求"时容易只拿到部分条文却以为拿到全部。节块会抢占真正该命中的条文块名额。 |
| 条号识别用行首裸数字，不用 `第X.X.X条` | 真正的条款是裸数字格式（554 个），`第 X.X.X 条` 在 5 份中仅 4 处（民用 2、混凝土 1、钢结构 1）且都是跨条引用。 |
| 表格按 HTML 解析，行级自然语言化 | 全部文件含 `\|` 的行数为 0，表格是内联 HTML。渲染器会把它显示成正常表格，造成"已是 Markdown"的错觉。 |
| 前言与目次保留入库但不参与检索 | 合计占每份文件 10–13%，且含大量高频词与章节标题，直接参与检索会产生"命中标题而非条文"的假阳性。 |
| 标题内嵌空格保留在源文件，解析时内存归一化 | 用户决定先不改文件。解析器按标题文本判断类别并去空格，源文件保持转换工具原样，便于溯源与对比。 |
| 标准号由外部映射表提供 | 5 份文件全文不含标准号，文件名也不含，无法自动推断。 |
| 数值校验分层，推导层不做白名单 | 推导必然产生条文里没有的新数值，强校验会让所有需要算数的问题被误降级。 |
| top10 按 `clause_id` 聚合而非按块 | 长条文按款切分后，多个块可能只对应同一条。 |
| `scope` 块不占 top10 名额 | 否则会出现"依据里有一条不能当依据"。 |
| `term` 块可作依据 | 术语章属规范正文，定义具有约束力。 |
| 同义词追加进查询文本而非多路检索 | 单次编码成本最低，对 dense 影响小、对 sparse 有明确增益。 |
| 查询中的数值剥离后再检索 | 数值对语义检索是噪音。 |
| 未命中阈值用自动题库标定，初始保守 | cross-encoder 绝对分值不可跨模型迁移，必须有标注数据。 |
| 输出用 Markdown + 分隔标记而非 JSON | JSON 会让流式渲染必须等完整响应。 |
| 上下文超限丢整条而非截断 | 截断可能砍掉条款的例外情形，比少给一条依据危险得多。 |
| 项目条件手改后锁定 | 否则"可见可改"形同虚设。 |
| 重排默认开启，思考默认关闭 | 重排是每次都一样的 0.5–1 秒小额支出且有正收益；思考会把答案正文推迟 30–65 秒，只在少数需要前提检查的问题上值得。 |
| GPU 不可用时不回退 CPU 重排 | CPU 重排需 10–25 秒，比直接放弃重排更糟。 |
| 两个本地模型常驻 GPU | 实测空闲显存 5.6 GB 宽于空闲内存 3.9 GB。 |
| 用 PyTorch + FlagEmbedding 而非 ONNX | bge-m3 多输出导出麻烦；ONNX Runtime GPU 需 DLL 严格匹配且装错会静默回退 CPU。 |
| 运行时用 PyTorch 自带 CUDA runtime，不引用系统 Toolkit 库文件 | 轮子需在任何装了足够新驱动的机器上可运行；Windows 上 torch 从自身 `lib/` 加载 DLL。 |
| 保留 CUDA Toolkit 12.6 供编译类依赖 | 版本与 cu126 一致，将来编译 CUDA 算子不会版本错配。 |
| 禁止用 conda 装 PyTorch | conda 渠道的 `cudatoolkit` 与 pip 轮子的 runtime 冲突。 |
| 新建 conda 环境而非复用现有环境 | 避免本项目依赖与历史实验混在一起。 |
| 开发与部署同机但数据隔离 | 调试入库时误覆盖正式 collection 的重建成本极高。 |
| 不配 CI，本地跑 ruff + pytest | 内网自用项目，代码不上公网。 |
| 不做 Milvus GPU 索引 | 库内仅 554 条条款向量，CPU 检索不足 100 ms。 |
| 不引入本地小模型 | 批处理走 API 总成本不足 1 美元。 |
| Milvus 只存索引不存原文 | 避免两处存储不一致。 |
| 不建 FTS5 + jieba | bge-m3 的 sparse 输出可承担关键词召回。 |
| 查询改写按需触发 | 每轮改写要多等 1.5–3 秒，而自足问题无需改写。 |
| 强制性条文不做额外标记 | 原文用词（必须/严禁、应/不应、宜/可）已承载效力等级。 |
| 只做标准级失效提示，不做条文级映射表 | 条文级映射需逐条比对废止清单，工作量数百条。 |
