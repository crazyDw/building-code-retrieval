# 建筑规范 RAG 智能检索助手 · 项目概况

## 一、摘要

面向工程设计人员的规范检索助手，部署在内网单机，Web 界面访问。用户用自然语言描述设计场景，助手定位到具体规范条款，输出**分层答案**：基于条文的条件性推导在前，条文原文与适用范围在后，二者视觉严格区分。

**允许条件性推导，禁止下合规结论。**

**语料已就位**：5 份规范 Markdown，共 33 章 / 91 节 / 554 条 / 436 款 / 7 项，存放于 `数据库上传资料/`。**标准号映射表已就位**：`数据库上传资料/规范标准号映射表.md`（2026-10-05）。

### 技术选型

后端 FastAPI；前端 React + Vite + TypeScript；向量库 Milvus（Docker standalone，数据目录配置到 D 盘）；关系库 SQLite；嵌入模型 bge-m3；重排模型 bge-reranker-v2-m3；生成走 DeepSeek API，**经 LangChain 的 DeepSeek 集成调用**（LangChain 只用于生成侧，检索链路自研，见《关键决策记录》）。

**设备分配与资源预算**

- **两个本地模型常驻 GPU（fp16）**：bge-m3 约 1.2 GB + bge-reranker-v2-m3 约 1.2 GB + 激活开销 1–2 GB，合计 3.4–4.4 GB。选 GPU 而非 CPU 的原因是**显存比内存宽裕**（空闲显存 5.6 GB vs 空闲内存 3.9 GB）。
- **内存是更紧的一环**：Milvus 三件套在 WSL2 内需 1.5–2 GB，部署时通过 `.wslconfig` 限制其上限。
- **启动预热**：服务启动时加载两个模型并各跑一次空推理，**预热完成前不接受请求**。
- **图片资源**：当前 5 份语料均不含图片；若后续规范的 Markdown 含插图，图片存于文件系统，SQLite 仅存路径。

**延迟分解（检索侧）**：查询编码 10–30 ms + 双路检索 50–100 ms + 重排（25 条候选）约 800–1700 ms + 回表约 10 ms，合计 0.9–1.9 秒。API 侧是剩余延迟主体，须在实施第一步实测校准。

### GPU 与 CUDA 配置

**结论：GPU 推理全程使用 CUDA，只需 NVIDIA 驱动与 PyTorch 自带的 CUDA runtime；本机已装的 CUDA Toolkit 不参与运行，但版本与 PyTorch 一致，保留供编译类依赖使用。**

| | 里有什么 | 如何使用 |
|---|---|---|
| NVIDIA 驱动（610.74） | `nvcuda.dll` 等 | **必需**，没有它 GPU 完全不可用 |
| CUDA Toolkit（12.6） | `nvcc`、头文件、静态库、cudart | **运行时不使用**，仅编译自定义算子时需要；版本与 cu126 一致 |
| CUDA Runtime | 运行 CUDA 程序需加载的动态库 | **必需**，由 PyTorch 轮子自带 |

**为什么 PyTorch 自带 runtime 而非复用系统 Toolkit**：轮子需保证同一份产物在任何装了足够新驱动的机器上可运行，不能依赖用户装的 Toolkit 版本（CUDA 库跨小版本 ABI 不保证兼容）。Windows 上 torch 从自身 `lib/` 目录加载 DLL，不查 PATH。

**安装命令必须显式指定索引**：

```
pip install torch --index-url https://download.pytorch.org/whl/cu126
```

直接 `pip install torch` 可能装到 CPU 版，届时 `torch.cuda.is_available()` 返回 `False` 且**不报错**。

**禁止用 `conda install pytorch`**：conda 渠道会额外装一套 `cudatoolkit`，与 pip 轮子自带的 runtime 冲突。

**验证**：

```
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

**两个常见误解**：`torch.version.cuda` 是 PyTorch 自带的 runtime 版本，与系统 Toolkit 版本不要求相等；`nvidia-smi` 显示的 `CUDA Version` 是**驱动支持的最高版本**，不是已安装版本。

### 五级层级与识别规则

规范正文的层级为 **章 → 节 → 条 → 款 → 项**。判定依据是**行首文本的编号形态**，不是 `#` 标记的数量。

| 层级 | 行首形态 | 正则 | 样例 |
|---|---|---|---|
| 章 | 标题行 + 单段数字 | `^\d+(?:\s\|$)` | `# 1 总 则` |
| 节 | 标题行 + 两段数字 | `^\d+\.\d+(?:\s\|$)` | `## 3.1 混凝土` |
| 条 | 行首三段数字 | `^\d+\.\d+\.\d+\s` | `1.0.1 为规范民用建筑…` |
| 款 | 正文行首单段数字 | `^\d+\s+\S` | `1 应按照可持续发展的原则…` |
| 项 | 正文行首数字 + 右括号 | `^\d+[）)]` | `1）与镀锌钢材或铝材相接触部位…` |

**章与款同形**（都是"数字 + 空格"），靠位置区分：章在标题行、款在正文行。

**归属规则**：条归属于最近的上级节，该章无节时直接归属其章（实测 3 处：民用建筑通用规范第 1 章，住宅项目规范第 1、5 章）；款归属于最近的上一条；项归属于最近的上一个款。

**项不单独成块**，切分方式见下方「分块策略 › 切块规则」。

### 解析器必须容错

外部转换工具的输出在不同文件间形态不一，实测过四类缺陷：

| 缺陷 | 表现 | 后果 |
|---|---|---|
| 章标记混用 | 同一文件里部分章用 `#`、部分用 `##` | 按 `#` 数量判层级必然出错 |
| 章与节全同级 | 整份文件的章和节都用 `##` | 同上 |
| 目次条目带标记 | 目次里某条被写成 `## 8 维护与拆除…… 19` | 章数多算；正文起点被误定在目次内部 |
| 条文被标为标题 | `## 3.2.1 普通钢筋的材料分项系数…` | 该条从条款列表消失，条数少算 |

四类缺陷在首批 5 份语料中都实际出现过，且**同一文件内也可能不一致**（混凝土结构通用规范里 `3.2.1`~`3.2.3`、`4.4.7`~`4.4.14` 曾被标为标题，而 `3.2.4`、`4.4.10` 是正常条文）。

**目次区间不能靠"第一个章标题"界定**，正确做法是：从文本为「目次」的标题行起，跳过行尾带页码的内容行（`\s\d+\s*$`），到第一个既匹配章/节模式又不带页码的标题行止。

### Markdown 解析规则

**1. 条号识别用行首裸数字，不是 `第X.X.X条`**

- 真正的条款是 `1.0.1`、`7.5.6` 这种行首裸数字（5 份合计 554 个）。
- `第 X.X.X 条` 在 5 份文件中合计仅 **4 处**（民用 2、混凝土 1、钢结构 1），且都是**跨条引用**，应抽为引用图的边，不作层级依据。

**2. 条款分隔依赖「条号行首」+「行尾双空格」**

- 行尾双空格是 Markdown 硬换行，但数量与条款数**在两个方向上都不吻合**：偏少的如住宅 120 vs 122、民用 140 vs 142；偏多的如混凝土 106 vs 99、砌体 102 vs 84、钢结构 126 vs 107（最多差 19）。**须以条号行首为主、双空格为辅**。

**3. 表格是 HTML，且可能有合并单元格**

- 全部文件含 `|` 的行数为 **0**，Markdown 表格分隔行数为 0。渲染器会把内联 HTML 显示成正常表格，造成"已是 Markdown"的错觉。
- 解析器必须解析 `<table>/<tr>/<td>`，并按 `colspan` / `rowspan` 展开：`colspan` 的值填充到其覆盖的每一列，`rowspan` 的值填充到其覆盖的后续每一行。
- **表题独立成行**（`表 2.2.6 住宅建筑的设计工作年限`），须与表格关联。
- **表格后的「注：」属于该表格的一部分**，是适用范围限定；注可能**带编号**，须整段保留。
- **一条可以对应多张表**（条文 3.1.1 同时引用 `表 3.1.1-1` 与 `表 3.1.1-2`），「条→表」是一对多。

**4. LaTeX 是符号而非公式，须还原**

- 5 份合计 **97 处行内符号**（混凝土 33 / 砌体 30 / 住宅 28 / 钢结构 5 / 民用 1），绝大多数是单位与符号：`$0.50 \, m^{2}$`（面积）、`$E_{h,\text{av}}$`（水平照度平均值）、`$R_{a}$`（一般显色指数）、`$L_{\text{eq,T/1}}$`（噪声指标）；另有砌体 3.4.2 一处 `$$…$$` 独立公式，保留 LaTeX 原文、不参与数值校验。
- **还原为可读文本**（`Eh,av`、`Ra`、`Leq,T/1`），并把**符号 ↔ 中文术语的映射写入查询扩展表** —— 用户不会输入 `E_h,av`，他会问"水平照度平均值"，原文若只有符号则向量与关键词都匹配不上。
- 真正的数学公式若出现，保留 LaTeX 原文，不参与数值校验。

### 分块策略

**主键体系**

- `clause_id`：**逻辑主键**，标识"条"，如 `{标准号}_5.3.9`（标准号来自外部映射表）。
- `chunk_id`：**物理主键**，标识检索块；一条对多块。
- `section_id`：节标识；章下无节的章节其 section 标识退化为章号。
- `table_id`：表标识，如 `表 3.1.1-2`。

**块类型**：`body`（条文正文）、`table_row`（表格行）、`scope`（适用范围限定）、`term`（术语条目）。

**切块规则**

- 主粒度为「条」。条文长度中位数为 47–54 字，多数条文天然整条成块。
- **超过 256 token 的条文按「款」（行首序号段落）切分**，每款一块，共享 `clause_id` 并标注款号；款块自身仍超限时的切分方式见下一条。
- **条超限但无款时退化为按句切分**：若该条是整段叙述、没有款，按句切分，每句一块，共享 `clause_id`。M2 实测 11 条超限条文全部含款，此分支仅由合成夹具验证，属兜底。
- **款项打包成块；超限时在项边界切分**：款连同其下的项打包为一块。超过 256 token 时**在项边界处切分**为多块，每块包含完整的项，共享 `clause_id` 与款号 —— 项与款共享前置条件（如「严禁用于下列混凝土结构：」），劈开会让每一片都失去适用前提；切分也不得跨款。**单个项自身超过 256 token 时，保留整项作为一个超限块并记录例外，不劈项（铁律 11 优先）。**
- **项不脱离的是款的标识，不是款的物理块**：切分后每块都带款号，任何时候都能定位回所属的款。
- **按款切分时，条的引导句单独成块**：款之前的正文（如"……应符合下列规定："）不属于任何款，单独切为一块。它本身几乎不会被召回，但命中后组装时仍会还原为整条，因此不影响答案完整性；独立成块是为了让"按款切"这条规则没有例外分支。**整条不超限、不触发切分时，引导句仍留在整条块内，不单独成块。**
- **这不是边缘保护，是需要真正实现的功能**：M2 用真实 tokenizer 实测，按块文本（标准名 + 章节路径 + 条号 +（款号）+ 正文）计量，全语料共 **11 条超限**：住宅 `4.2.2`(281) / `4.2.7`(258)，钢结构 `7.2.4`(261)，混凝土 `3.1.4`(300) / `4.4.7`(285) / `4.4.9`(299)，砌体 `4.1.6`(268) / `4.3.1`(311) / `4.3.2`(315) / `4.3.3`(277) / `4.4.3`(276)；住宅 `4.2.4` 为 233，不超限。11 条全部按款切分。
- **长度按实际块文本计量（含标准名与章节路径前缀），不含其引用的表格**：表格内容归入 `table_row` 块，不参与条文块的长度。若把表格文本计入，住宅 `3.1.1`（含表 829 字）会虚增为超限，但其正文块实测 76 token，不切分。
- 每个块以 256 token 为硬上限，与重排截断对齐；唯一例外是**单个项自身超过 256 token**（M2 实测本批语料 0 例外；合成夹具验证例外标记）。
- M2 全量结果：701 块（body 601 / table_row 100），无未标记超限块。

**嵌入文本格式**

- 正文块：**「标准名 + 章节路径 + 条号 +（款号）+ 正文」**。整条块与引导句块不带款号，款块带款号。加入章节路径是因为短文条（最短 11 字）的向量高度泛化，带上主题词可显著提升区分度。
- 表格行块：「标准名 + 表名 + 表题 + 表格注 + 行内容」。表题与「注：」并入前缀，使其**可被检索**（否则用户问"托儿所的楼梯踏步"会命中表行却漏掉限定条件）。

**表格**：解析 HTML 并按合并单元格展开后，**每行拼上表头维度转成自然语言句子**，与结构化字段一并入索引。例：`以电梯作为主要垂直交通的高层和超高层建筑楼梯，踏步最小宽度 0.25m、最大高度 0.180m`。

**公式**：符号类还原为可读文本；真正的数学公式保留 LaTeX 原文，不参与数值校验。

**前言与目次**：**入库留存但不参与检索** —— 不建向量、不进入召回候选、不出现在引用列表。两份文件的前言与目次合计占 10–13%，且含大量高频词与章节标题，直接参与检索会产生"命中标题而非条文"的假阳性。

**术语章节**：规范自带的"术语"章节逐条成块（`term`），**可作为答案依据** —— 术语章属规范正文，定义具有约束力。

**适用范围说明**：独立成块（`scope`）。可被检索，**但不得作为答案依据**，只能作为限定条件附加在答案旁。

**块元数据**：`chunk_id`、`clause_id`、`section_id`、标准号、标准名、层次、版本、章节路径、**章号/节号/条号的数值分量**、节内条文总数、条号、款号、来源文件、块类型、是否含表格、`table_id`、`row_no`。

> 条号必须存**数值分量**（或补零排序键）：字符串排序会把 `5.3.10` 排在 `5.3.9` **前面**，章节树、条文列表、引用排序全都会错。

### 入库与校验

- **Markdown 格式校验（每部新文件入库前必跑）**：用本项目技能 `normalize-regulation-md` 的普查脚本检查条号数量与连续性、标题层级、标题是否含内嵌空格、表格形式、是否含前言与目次。校验结果**报告但不阻断**（解析器已容错）；仅在条号数量与连续性异常时阻断入库。
- 入库硬校验：同一标准号只允许一个现行版，违反则拒绝入库。
- **解析事务性**：解析、切分全部完成后一次性写入，任一步失败即整体回滚。
- **标准级失效提示**：命中已被全文强制性规范替代的老标准时，在答案末尾提示"该标准部分条文已被全文强制性规范替代，请核对适用性"。不做条文级替代映射表。
- **术语词典与别名表**：
  - 术语候选由统计方法（互信息、左右熵）加规范自带术语章节自动抽取，不需要模型参与；再由 DeepSeek API 生成设计人员常用说法。人工审核保留 **300–500 个高频核心词**。
  - **查询扩展表须覆盖两类映射**：表格条件词（"喷淋" → "自动灭火系统"）与 **LaTeX 符号 ↔ 中文术语**（`Eh,av` → 水平照度平均值）。
  - 为每部规范维护别名表（标准号 + 全称 + 常用简称），用于识别用户点名。
- 每部规范入库后自动生成 **50 条随机核对清单**（条文原文 + 解析出的条号/页码），供人工约 10 分钟过一遍。

## 四、检索链路

### 查询理解（按此顺序，可短路）

1. **条款号短路**：识别到纯条款号模式时直接查原文返回，不走检索与生成。
2. **标准号别名匹配**：完整匹配别名表时才限定检索范围（避免"这个防火门"被误判为限定"防火规范"）。
3. **数值抽取**：把提问中的数值抽为条件，检索时使用剥离数值后的场景描述，推理阶段再代入。
4. **按需查询改写**：仅当出现指代词或问题长度少于 10 字时才改写为独立问题。
5. **同义词追加**：把命中的术语别名（含符号映射）追加进查询文本，单次编码。

### 召回与排序

- **索引结构**：bge-m3 一次前向同时产出 dense（1024 维）与 sparse 向量，均存 Milvus。dense 做语义召回，sparse 承担关键词召回，因此**不使用 SQLite FTS5 + jieba**。
- **Milvus 配置**：FLAT 索引 + COSINE 度量；标量字段存 `standard_id`、`level`、`chunk_type`、`clause_id`、`section_id`。
- **职责边界**：SQLite 是唯一真相源（原文、元数据、引用图、词典），Milvus 是纯派生物。
- **融合**：dense top30 + sparse top30 → RRF 融合（默认等权）→ 取 **25 条候选块**。
- **重排**：**GPU 重排默认开启**（截断 256 token，与块上限一致，因此正常路径下不会截断任何块）。`RERANK_ENABLED` 作为运维开关，状态通过界面与日志暴露。
- **聚合**：按 `clause_id` 聚合，每条取最高分，取 **top 10 条**。
- **重排候选数与延迟的冲突（须实测确认）**：候选 25 条时首字可能顶到 3 秒红线，若不达标则回调至候选 20、返回 8。
- **`scope` 块不占 top10 名额**：命中时作为限定条件附加，空出名额从候选补一条正文块。
- **未命中判定**：重排分低于阈值即判未命中。**阈值用自动题库标定**（正负样本分数分布的区分分位点），初始取保守。
- **GPU 降级**：自动跳过重排，用 RRF 分数取 top10，置 `degraded_flag` 并在界面提示。不回退 CPU 重排（CPU 重排需 10–25 秒，比直接放弃更糟）。

### 引用图

- **以「条→表」为主、「条→条」为辅**：实测住宅项目规范有 10 处表引用、0 处条引用，与另一份的比例相反。
- 正则抽取覆盖：`应符合表X.X.X的规定`（主要）、`应符合第X.X.X条`、`见第X.X.X条`、`按第X.X.X条规定`、`应符合GB XXXXX的规定`（跨标准引用单独建边类型）。
- **一跳扩展最多 5 条**，排在主条款之后，**不参与重排**，标注为关联参考、不得作为结论依据。

### 上下文组装

- 命中某一块时，**送入模型的是整条条文（含各款，以及该条引用的表格），并标出命中哪一款**。长条文与表格行虽各自被切块，入上下文时都还原到所属的条。
- 对同时引用多张表的条文（如 `3.1.1` 引用 `表 3.1.1-1` 与 `表 3.1.1-2`），整条即包含两张表。选哪张表的判据写在条文正文里，一并送入可让模型据此判断。
- 携带章节路径；该节有 `scope` 块时一并带入。
- **上下文上限 12000 token**。按 top10 条估算约 500–3000 字，通常远低于上限；若命中多条长条文则可能接近，此时从重排分最低的条开始整条丢弃，不做单条截断。

## 五、生成与答案形态

**默认路径**：`deepseek-flash` + `thinking: disabled`。

**深度分析（用户主动触发）**：`deepseek-flash` + `thinking: enabled` + `reasoning_effort: low`，候选提高到 40 条、返回 top 16。

- 系统提示词设计为**固定前缀**（含术语表）以命中上下文缓存 —— 缓存命中价是未命中的五十分之一。
- 思考模式不支持 `temperature`；`top_p` 仅在思考模式生效且区间限制在 0.95–1.0。参数按模式分别配置。
- API 超时 60 秒，失败重试 1 次，仍失败走降级。

### 输出格式

- 模型输出 **Markdown + 自定义分隔标记**（`<!--推导-->`、`<!--原文-->`），不用 JSON —— JSON 会让流式渲染必须等完整响应，且长文本转义易出错。
- **条号引用由模型显式用标记包裹**，前端按标记渲染为可点击引用，不靠正则猜（正则会把正文里提到的其他条号错误链接）。

### 数值一致性校验（分层）

- **原文层**：带 `clause_id` 的逐字引用，其中的数值必须出现在该条原文中，未匹配则重生成。
- **推导层**：**不做数值白名单校验** —— 推导值（如由"6 层、层高 3 米"算出"约 18 米"）本就不在条文里，强校验会让所有需要算数的问题被误降级。改为**强制模型写明所用输入值**（"按层数 6、层高 3.0m 推算"）以便人工核对，并将推导数值记入日志供复盘。
- 两处共用同一套数值抽取逻辑。

### 思考模式的作用

思考模式要求模型在给出答案前先输出推理草稿。它**并非对所有任务都有增益**。

**能够受益的四类任务**

1. **适用范围判断** —— 提取条文的适用范围条件，与会话项目条件比对。
2. **建筑分类推导** —— 由层数、层高、使用性质推出建筑高度与分类，据此选择正确的条文或表格行次。
3. **多条文归位** —— 命中的多条条文可能分别适用于不同条件，需分别判断适用性。
4. **多步条件推导** —— 分类判定 → 行次选择 → 附加条件放宽规定的链式应用。

**无增益、开启只会增加等待的任务**：单条条文原文抽取、数值读取与比对、定义类问题。

**典型差异示例**

问题："6 层住宅，层高 3.0 米，设自动灭火系统，防火分区最大能到多少？"

- 默认路径：从命中的表格行读取数值并给出答案，但可能未先判定该建筑约 18 米、属多层住宅而非高层，从而引用错误的表格行。答案表面完整，不确定之处不会显现。
- 深度分析：先判定建筑分类，核对耐火等级，再选择对应行次并应用放宽规定，输出时附带前提说明。

思考模式的核心价值不只是"更准"，而是**更愿意停下来检查前提**。本系统中最危险的错误不是答不出来，而是答案流畅但前提用错。

**定位**：默认关闭，作为按需的质量档与复核工具 —— 用户可先取得快速答案，对结论存疑时再触发。

**局限**：默认路径不主动推演建筑分类，仅对条文自带的适用范围说明做字面比对。

### 其余输出规则

**提示词约束**：只依据给定条文作答；每条结论挂 `clause_id`；命中全文强制性规范时明确标注；允许条件性推导、禁止合规结论；禁止引入规范外知识；`scope` 块与表格的「注：」不得作为独立依据，只能作为条件限定。

**答案分层与顺序**：推导在前，条文原文与适用范围在后，两块用明显不同的视觉样式区分。

**多规范命中**：命中的全文强制性规范放主依据位置，其他标准作补充依据分开列。不做对比分析。

**失败模式**：未命中时明确输出"未检索到直接依据"并列出最接近的条款，不编造；API 不可用或超时时降级为纯检索模式，照常返回条文原文与条款号并明示"当前未提供归纳解读"。

## 六、界面、会话与接口

- **界面**：问答区、引用侧栏（可展开条文原文，**引用卡片显示完整章节路径**如"第5章 建筑通用空间 › 5.3 楼梯、走廊 › 5.3.9"）、条款号直查、一键复制带出处的 Markdown 引用文本、**项目条件条**、**「深度分析」按钮**。
- **表格展示**：命中表格时**展示整张表并高亮命中行** —— 表格各行是互斥对比关系，只看一行容易套错条件。
- **章节完整性提示**：答案中若有多条来自同一节，标注「**该节共 N 条，当前列出 M 条**」并提供「查看该节全部」入口，避免用户以为拿到了全部。
- **项目条件条**：自动抽取使用性质、层数、建筑高度、耐火等级、是否设自动灭火系统等参数；**用户手改的条目标记为锁定，模型不得覆盖**。
- **上下文**：只带本轮召回条款，加上被显式引用过的历史条款（识别方式：用户消息中出现条号，或用户点击了引用链接），不累积。
- **宽泛问题**（如"6 层住宅该注意什么"）：引导收敛到具体方面，同时给 8–10 条起步条文，并注明"这不是完整清单"。
- **多子问题**：反问澄清先回答哪一个。
- **深度分析展示**：流式展示推理过程，放在折叠面板 + 明显不同底色中，标注"以下为模型推理过程，非规范内容"。

**接口**

- `POST /api/chat`：SSE 流式，请求含 `deep_analysis` 开关；返回 `{answer_delta, reasoning_delta, citations[], tables[], section_hint, fallback_flag, degraded_flag, rerank_used, superseded_notice, project_conditions}`
- `GET /api/health`：就绪状态、预热状态、GPU 可用性
- `GET /api/clause/{clause_id}`：条文原文与元数据
- `GET /api/clauses?standard_id=&section_no=`：该节全部条文（支撑「查看该节全部」）
- `GET /api/standards`：已入库规范清单与章节树
- `GET /api/search?clause_no=5.3.9`：条款号直查
- `POST /api/ingest`：单部规范入库，幂等，触发 Milvus 全量重建
- 环境变量：`DEEPSEEK_API_KEY`、`BASE_URL`、`MODEL`、`REASONING_EFFORT`、`EMBED_MODEL`、`RERANK_ENABLED`、`RERANK_MODEL`、`RERANK_MAX_TOKENS`、`CHUNK_MAX_TOKENS`、`CONTEXT_MAX_TOKENS`、`TOPK_DENSE`、`TOPK_SPARSE`、`RERANK_CANDIDATES`、`TOP_N_DEFAULT`、`RERANK_CANDIDATES_DEEP`、`TOP_N_DEEP`、`REF_EXPAND_LIMIT`、`SCORE_THRESHOLD`、`MILVUS_URI`、`MILVUS_COLLECTION`、`SQLITE_PATH`、`STANDARD_MAP_PATH`、`DEVICE`、`DEV_MODE`
- 检索日志：每轮提问、召回块与所属条款、融合分数、重排耗时、阈值判定、是否兜底、是否降级、推导数值，落本地文件（JSON Lines）。

## 七、验收标准与测试

### 语料解析

- **条号解析**：5 份共 554 条全部识别，编号零缺口；校验规则须正确放行两类跨章过渡（有节的章首条 `X.1.1`、无节的章首条 `X.0.1`）。
- **五级层级**：章 33、节 91、条 554、款 436、项 7 与实测一致（款数校正说明见第三节）；项正确归属到所属款，且每个含项的块都带款号。
- **款项超限切分**：《混凝土结构通用规范》`4.4.9` 整条 299 token 按款切分（引导句 + 款1 + 款2）；款2 含 3 个项、实测 185 token，未触发项边界切分。项边界切分由合成超限款夹具验证（各块不跨项、均带款号、每块只含完整项）。
- **标题重建（两种形态都要过）**：对已规范化的 5 份解析正确；用未规范化的备份副本做回归，解析结果必须一致。
- **标题空格内存归一化**：解析出的章节路径中不含内嵌空格（`总则` 而非 `总 则`），且源文件未被修改。
- **目次排除**：验证钢结构通用规范正文起点为 L54 而非目次内的 L48；5 份文件的前置内容均未被识别为章或节。
- **条号排序**：验证 `5.3.9` 排在 `5.3.10` 之前。
- **表格解析**：HTML 表格全部解析成功；`colspan`/`rowspan` 正确展开；表题与「注：」（含带编号的注）正确关联且可被检索；验证条文 3.1.1 正确关联 `表 3.1.1-1` 与 `表 3.1.1-2`。
- **LaTeX 还原**：符号正确还原；符号 ↔ 中文术语映射写入查询扩展表，验证用中文术语能召回含符号的条文。

### 检索与生成

- **自动题库**：每条条文生成口语化问题（提示词明确**禁用条文原词**），源条文进入 top5 的比例 **Recall@5 ≥ 90%**。题库经 DeepSeek API 批量生成，总成本不足 1 美元。
- **对抗子集**：同义改写版本单独统计召回跌幅；**表格类问题单独统计**（验证"电梯作为主要交通"能否命中对应表行）；**符号类问题单独统计**。
- **阈值标定**：用正负样本分数分布的区分分位点确定未命中阈值，记录标定曲线。
- **分层数值校验**：验证原文层篡改能被拦截、推导层不因算出新数值被误降级。
- **分块校验**：除「单个项自身超限」这一例外外，全量检查所有块不超过 256 token；人工抽检切分边界语义完整性，重点检查住宅项目规范 `4.2.2`（281 token，住宅内最长）。
- **长度口径**：条文块的长度按正文计量，不含其引用的表格内容。
- **切分边界**：验证按款切分时引导句单独成块（整条未超限时不单独成块）；用含项的长款做单元测试，验证切分取项边界、不把项劈开。
- **长条文还原**：验证命中某一款时，送入模型的是整条而非仅该款。
- **聚合校验**：同一条的多块命中后正确聚合；top10 为 10 条不同条款。
- **环境校验**：`torch.cuda.is_available()` 为 True 且设备名正确；`torch.version.cuda` 与系统 Toolkit 版本一致；两个模型均以 fp16 常驻 GPU。
- **延迟**（须实测校准，推算值不作为最终依据）：
  - 默认路径：首字（答案正文第一个字）≤ 3 s，完整回答 ≤ 20 s。**候选 25 条时首字为风险项，须重点实测**。
  - 深度分析：首字（思考流第一个字）≤ 5 s，完整回答 ≤ 90 s；同时记录"答案正文首字"。
- **重排基准**：25 条候选、256 token 截断下耗时，确认首字仍 ≤ 3 s；超标则回调候选至 20、返回 8。
- **GPU 降级 / 预热行为**：模拟显存不足或加载失败，验证降级与就绪状态正确。
- **开发模式**：验证 `DEV_MODE=true` 时跳过重排与模型加载、使用 `_dev` 数据源、热重载可用。
- **引用图**：`条→表` 边正确建立（住宅项目规范 10 处）；`条→条` 边正确建立；一跳扩展不超过 5 条且不参与重排。
- **章节完整性提示**：构造问某一节的查询，验证标注节内总条数且「查看该节全部」返回正确条文集合。
- **表格返回**：验证展示整表且命中行高亮。
- **条件性推导**：推导与所引条文一致、保持原文用词等级、不出现合规结论措辞。
- **思考模式有效性**：需要分类推导的问题在深度路径下应显式完成判定并说明前提。
- **项目条件**：手改后锁定，后续轮次不被覆盖。
- **多轮与短路**：按需改写在指代场景触发、自足问题不触发；条款号输入正确短路。
- **兜底与降级**：超范围问题拒答并给出最接近条款；断网时仍返回条文并标记 `degraded_flag`。
- **代码质量**：ruff 与 pytest 本地全绿。
- **上线后复盘**：部署两周后从未经筛选的检索日志中抽查 20 条真实提问。

## 八、假设、默认值与不做范围

**待确认项**：见第三节「待确认项」——标准号映射表已解决、条文说明与附录分支已定（v1 不做）、转换质量按 M1 回归方案处理。

**假设与默认**：PDF → Markdown 的转换由外部工具完成，其输出可用；规范片段与用户问题可发往外部 API；规范版本时效由人工判定并写入元数据；一次性交付（含格式校验脚本、入库脚本、词表审核流程、操作说明）；服务通过 Windows 服务或任务计划开机自启，内网绑定访问；备份为"Markdown 语料 + SQLite 单文件 + Milvus 卷快照"；SQLite 开启 WAL；`.wslconfig` 限制 WSL2 内存上限；Milvus 用 FLAT 索引 + COSINE 度量；RRF 默认等权。

**成本参考**：默认路径按每次约 8000 输入 + 1000 输出 token 估算，谷时单次约 $0.002；深度分析因思考 token 计入输出，单次约 $0.003–0.005。自动题库与词表生成的批量调用总成本不足 $1。

**v1 明确不做**：PDF → Markdown 转换本身；按专业拆分章节；源文件标题内嵌空格的批量清理；**地名 → 建筑气候区划的查询扩展**（表格里的气候区划用代号表示，如"II、VI"，而用户多用"北京"这类地名提问，两者对不上；留待后续版本完善）；合规判定与参数化规则引擎；跨规范新旧体系并列对比；条文级失效映射表；地方标准与图集；节级检索块；会话历史持久化、用户反馈纠错闭环、模型微调、账号与权限；Milvus GPU 索引；本地大模型生成；CI 流水线。
